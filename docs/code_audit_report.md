# Code Audit Report — PS 26160 AI-Powered IPsec VPN Protocol Analyzer

> Audit method: every source file was read in full (not just grepped for function names). The ML pipeline, countermeasure simulator, and pytest suite were **actually executed** against the live repo to verify that claimed numbers reproduce. No code was modified during this audit.
> Date: 2026-09-22

## Summary table

| Stage | Status | Specific Issues Found | Severity |
|---|---|---|---|
| **Testbed generation** | Broken (unexecuted) | Config generation for all 8 required variants is correct and matches `build_log.md`'s matrix exactly (verified `gen_configs.py` output against the 8-variant table). `docker-compose.yml`, `switch_config.sh`, `test_all_configs.sh` are structurally sound. **But** `testbed/test_results.log` shows every one of the 8 variants as `FAIL (SA: DOWN)` — the testbed has never once established a real IPsec SA. `gen_configs.py` hardcodes an absolute Windows path (`d:\Downloads\26160\testbed`), making it non-portable. `setup_strongswan.sh` uses the legacy `ipsec.conf`/`ipsec.secrets` format that `research_dossier.md` explicitly says to avoid ("use swanctl.conf, not the deprecated ipsec.conf") — it's dead, contradicts the docs, and isn't called by anything. | Critical |
| **Traffic capture** | Missing | There is no dataset. `testbed/scripts/generate_traffic.sh` (the capture driver) was never run — it depends on the testbed above. `feature_extractor.py`'s `batch_process()` reads a manifest at `../data/raw/dataset_manifest.csv`, which does not exist anywhere in the repo (no `data/raw/` directory at all). The only pcap-like artifact in the repo, `dummy.pcap`, is 5 literal ASCII bytes (`b"dummy"`) written by `backend/run_e2e_timing.py`/`test_api.py` — not a valid pcap. Of the 48 PCAPs `build_log.md` targets, 0 exist. | Critical |
| **IKE parser** (`parser/ike_parser.py`) | Unverified / likely broken on real traffic | This is real logic, not a stub — but it does **not** use Scapy's typed field access at all. It calls `pkt.show(dump=True)` on every matching packet and then does substring search (`"AES_GCM_16_256" in pkt_repr`, `"Group 19" in pkt_repr`, etc.) against the dumped text tree. This is fragile: it assumes Scapy's default dissector renders IKEv2 payloads with these exact literal tokens, which is not guaranteed (Scapy's built-in ISAKMP/IKEv2 layer support is minimal and version-dependent), and it has **never been run against a single real captured packet** (no PCAPs exist — see Capture row). The only test for it (`tests/test_rule_engine.py::test_parser_extraction_mocked`) mocks `.show()` to return a hand-crafted string containing exactly the tokens the parser looks for, so the "passing" test proves the string-matching works on contrived input, not that it correctly parses real IKE traffic. This test is also currently **SKIPPED** in this environment (scapy isn't installed here). `rdpcap()` loads the entire pcap into memory and calls the expensive `.show(dump=True)` string-formatter per packet — inefficient for anything beyond toy captures. | Critical |
| **Rule engine** (`parser/rule_engine.py` + `nist_rules.json`) | Working | This is the one stage that is genuinely correct and verified. Severity-cap logic matches the NIST matrix in `research_dossier.md` exactly (IKEv1→25, DES/NULL/MD5→25, 3DES/weak DH→59, CBC/SHA1→79, AEAD/strong DH→100, no-PFS→cap 59). I ran the test suite myself: **10/10 rule-engine tests pass**. No hardcoded/fake outputs — scores are genuinely computed from the input dict via `min()` over applicable caps. Minor: category matching uses cascading substring checks (`"3DES" in val`, `"DES" in val and "3DES" not in val`) which is a little brittle but is explicitly guarded against the "2 in ECP_256" false-match case in a code comment, and is exercised correctly by the tests. | — (working) |
| **ML feature extraction** (`ml_pipeline/feature_extractor.py`) | Orphaned / unused | The real SPLT extractor (20-packet floor, bidirectional flow keying by sorted-IP+SPI, IAT/length stats via numpy) is correctly implemented and matches the design in `research_dossier.md` and `deploymentreality.md`. **However it is never actually used anywhere in the pipeline that produces the numbers in the docs.** It's dead code: nothing calls `batch_process()`, and its required input (`data/raw/dataset_manifest.csv`) doesn't exist. `rdpcap()` again loads the whole file into memory rather than streaming. | Critical (by omission — see Classifier row for why this matters) |
| **Classifier + calibration + SHAP** (`ml_pipeline/train_model.py`, `generate_synthetic_features.py`, `generate_iscx_features.py`) | Working code, but built entirely on fabricated data — critical honesty issue | I ran `train_model.py` myself. It genuinely executes RandomForest → `CalibratedClassifierCV` (Platt scaling) → `shap.TreeExplainer`, and reproduces **exactly** the numbers quoted in `build_log.md`: Lab accuracy/F1 = 1.0000/1.0000, "ISCX Generalization" accuracy = 0.9944 (delta ‑0.0056). So the numbers are not manually typed by a human/agent — they are program output. **But the underlying data is the problem:** `data/features.csv` is produced by `generate_synthetic_features.py`, which does not touch any PCAP or the feature extractor above — it directly fabricates per-class rows via `np.random.normal`/`uniform` with hand-picked, deliberately non-overlapping parameters per class (e.g. ICMP is given `std_len = 0.0` exactly; VoIP `mean_iat≈0.02` with `std≈0.002`). A Random Forest trivially gets 100% accuracy on data that was constructed by rule to be linearly separable — this is circular validation, not evidence of real traffic-classification skill. Worse: `generate_iscx_features.py`'s own docstring claims it "Simulates features extracted from the ISCXVPN2016 dataset," but it **never touches the real UNB ISCXVPN2016 dataset** — it's a second, independent `np.random` generator (different seed, added "jitter" term) with no connection to any real Skype/Netflix/email capture. I confirmed `testbed/scripts/replay_iscxvpn.sh` (the script that would do the real download+tcpreplay) is a placeholder that never executed (`build_log.md` admits: "Status: Script written. Awaiting execution environment"). This means the "ISCXVPN2016 Generalization Validation: 99.44%" claim — presented across `build_log.md`, `mbalevel0.md` Q7, and implied in the PPT deck's `[VALIDATED]` tag — is **synthetic-vs-synthetic self-validation dressed up as external real-world validation**. This is the single most serious honesty gap in the codebase. | Critical |
| **Countermeasure simulator** (`ml_pipeline/adversarial.py`, `adversarial_padding.py`) | Split: one dead stub, one working-but-overclaimed | Two unrelated implementations exist. **(a)** `adversarial.py` defines `AdversarialSimulator` with a completely different column schema (`min_packet_size`, `total_packets`, `total_bytes`) than every other module's dataframe (`mean_len`, `pkt_count`, etc.) — confirmed via grep that it is **never imported or instantiated anywhere**. Pure dead code/stub. **(b)** `adversarial_padding.py` is the one actually wired up — I ran it and it reproduces the exact numbers in `docs/countermeasure_results.md` (MTU: 14.2% overhead, confidence 90.6%→77.0%; Adaptive: 17.0% overhead, 90.6%→87.3%), so these are genuinely computed, not invented. But two things undercut the claim: (1) the "adaptive dummy injection" is not a real per-packet WTF-PAD state machine — it's a crude linear rescaling of aggregate summary columns (`std_len *= 1.5`, `mean_iat /= multiplier`, etc.), a much weaker fidelity than the "WTF-PAD Inspired" framing implies. (2) `apply_mtu_padding()` only overwrites length-based columns and leaves every timing column untouched, which is why **accuracy never drops (100%→100%) in either scenario** — the classifier still gets the right answer every time, just with lower `predict_proba` confidence. The docs state this honestly (100%→100% is printed as-is), but a technical judge could reasonably ask whether "confidence dropped" without "accuracy dropped" is actually blinding the adversary, or just making it less sure of an answer it still gets right. Also inherits the synthetic-data problem from the row above. | Critical (a: dead code) / Moderate (b: real but overclaimed fidelity) |
| **Backend** (`backend/main.py`) | Broken / fully stubbed | This is the most severe finding in the whole audit. `POST /api/v1/analyze` → `process_pcap()` **completely ignores the uploaded file's contents.** It never calls `IKEParser`, `SecurityRuleEngine`, `SPLTFeatureExtractor`, or loads `models/calibrated_rf_model.pkl`. It just writes one hardcoded dict into `analysis_results[analysis_id]` — literal `59`, `"voip"`, `90.6`, `14.2`, `17.0`, etc. — regardless of what file was uploaded. I confirmed this directly: `dummy.pcap` (5 bytes of the literal text `"dummy"`, not a valid pcap) is what `test_api.py`/`run_e2e_timing.py` actually upload, and the backend "successfully" returns the exact same VoIP/59-score/90.6%-confidence result it always returns. `GET /api/v1/export/{id}` is explicitly stubbed: `"download_url": "stubbed_for_demo"`, no PDF/CSV is generated at request time. The code comment admits this outright: *"Here we mock the background processing to return our known findings instantly."* If a judge uploads any pcap — even a blank one — the tool will report the identical finding every time. `syslog_emitter.py` is the one genuinely functional backend piece: it actually writes structured MITRE-tagged JSON to `logs/siem_syslog.jsonl` (verified against the log file). | Critical |
| **Dashboard** (`frontend/Dashboard.jsx`, `frontend/index.html`) | Split: one dead/broken component, one working (against fake data) | Two incompatible frontend implementations exist with no build tooling anywhere (no `package.json`, no bundler config in the whole repo). `Dashboard.jsx` fetches `http://localhost:8000/api/analyze` (missing the `/v1/` prefix the backend actually uses → 404) and expects a response shaped `report.security_assessment.risk_score` / `report.ai_analysis.average_confidence_score` / `report.protocol_parameters` — none of which match `backend/main.py`'s actual response shape (`compliance` / `classification` / `countermeasures`). This component would fail immediately against the real backend and is not referenced from `index.html` or anywhere else — it's orphaned dead code, likely a discarded earlier draft. `index.html` is a separate, self-contained implementation (React+Babel via CDN, no build step) with three persona tabs (CISO/SOC/Auditor) that **does** correctly match the backend's actual field names and calls the correct `/api/v1/...` endpoints. This one would render correctly — but only because it's faithfully displaying the backend's hardcoded fake numbers from the row above. | Critical |
| **Report generation** (`backend/report_generator.py`) | Hardcoded / stub-like | `generate_executive_report()` and `generate_technical_report()` build the PDFs entirely from literal Python string constants — `"90.6%"`, `"77.0%"`, `"Group 2 (1024-bit)"`, `"17.0% Overhead"` are typed directly into `pdf.add_metric(...)`/`pdf.normal_text(...)` calls. The function takes no arguments and reads no results object, JSON file, or database row — it cannot reflect a different analysis even in principle. It happens to reuse the same specific numbers that one run of `train_model.py`/`adversarial_padding.py` produced, so they aren't randomly invented — but the report generator has no live wiring to the actual pipeline; if the model were retrained tomorrow and produced different numbers, these PDFs would silently go stale. The one dynamic part is real: it does check `os.path.exists()` and embed the actual `shap_waterfall_voip.png` / `padding_tradeoff_curve.png` images if present. `docs/reports/Executive_Report.pdf` and `Technical_Report.pdf` are therefore a hand-authored template, not a generated report in the sense the PS asks for ("automatically generate Executive Report & Technical Report" from live assessment). | Critical |
| **Tests** | Minimal, and partly theater | Only `tests/test_rule_engine.py` is a real pytest suite: 10 tests pass (verified by running `pytest tests/ -v` myself), 1 test (`test_parser_extraction_mocked`) is skipped in this environment because `scapy` isn't installed. `backend/test_api.py` and `backend/run_e2e_timing.py` are **not** pytest-discoverable tests — no `assert` statements, just `print()`s against a live server. Because `main.py`'s endpoint is fully hardcoded (see Backend row), these scripts will "pass" (never throw) no matter what is uploaded, so they provide zero real regression protection despite being named/positioned as an "E2E test." There are no tests at all for `feature_extractor.py`, `train_model.py`, `adversarial_padding.py`, `report_generator.py`, or either frontend. | Moderate |
| **Architecture alignment** (deterministic vs. ML separation) | Clean in the library code, erased at the integration layer | At the module level the Tier-1/Tier-2 split the docs describe is real and well-bounded: `parser/` (rule_engine + ike_parser) never imports anything from `ml_pipeline/`, and vice versa — this is genuinely good, inspectable separation a judge could review favorably. **The problem is that `backend/main.py` — the only place that's supposed to wire these two tiers together into one pipeline — calls neither of them.** It fabricates a result that merely *looks like* the output of both tiers combined. So the codebase can honestly show a judge "here is our clean deterministic engine" and "here is our clean ML engine" as separate artifacts, but cannot currently demonstrate them actually running together end-to-end on a real input — the demo path is a Potemkin front over two real-but-disconnected engines. | Critical |

## Cross-cutting findings not tied to one stage

- **`requirements.txt` is incomplete.** It lists `pyshark` (never imported anywhere in the codebase — dead dependency) but omits `matplotlib`, `shap`, `joblib` (all required by `train_model.py`/`adversarial_padding.py`) and `fpdf`/`requests` (required by `report_generator.py`/`test_api.py`/`run_e2e_timing.py`). A clean `pip install -r requirements.txt` would not be sufficient to run half the repo.
- **Environment reproducibility gap:** in the environment this audit ran in, `scapy` and `pyshark` are not installed at all, meaning `ike_parser.py` and `feature_extractor.py` cannot even be imported successfully right now (their Scapy imports are wrapped in a silent `try/except ImportError: pass`, so the module loads but every name like `rdpcap`/`ISAKMP`/`ESP` is undefined, and calling `.parse()` or `.extract_raw_flows()` would raise `NameError` at runtime, not a clean error).
- **No `__init__.py` / packaging** — imports rely on `sys.path.insert(0, ...)` hacks in multiple files (`main.py`, `test_rule_engine.py`) rather than the project being an installable package; fragile if run from a different working directory.
- **Honesty-tag audit:** cross-checking `build_log.md`'s own "Data Honesty & Validation Checklist" against what the code actually does: the **countermeasure bandwidth/confidence numbers** are legitimately code-computed (confirmed by re-running `adversarial_padding.py`). The **"Lab Test Split" and "ISCXVPN2016 Generalization" numbers labeled `[VALIDATED]`** are code-computed but on entirely fabricated data with no real pcap or real external dataset anywhere in the loop — this is the most important thing to fix or re-word before presenting to judges, since it's the exact claim a technically literate judge (per your own `mbalevel0.md` Q&A prep) is primed to interrogate.

## What is genuinely solid

To be fair and not just critical: the **rule engine + NIST rules JSON** is correct, tested, and passes real tests. The **testbed configuration generation** (8/8 required variants) and **docker-compose topology** are well-designed and plausible, just never successfully executed. The **SPLT feature extractor** and **SIEM syslog emitter** are real, correct, working code — they're just not wired into the demo path. The ML training script's *mechanics* (RF, Platt scaling, SHAP) are implemented correctly, independent of the data-quality problem.
